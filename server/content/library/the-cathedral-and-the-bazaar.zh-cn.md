<h2 id="abstract">摘要</h2>

我解剖了一个成功的开源项目 fetchmail，该项目是对 Linux 历史所揭示的软件工程出人意料的理论进行的一次有意识的验证。我通过两种根本不同的开发模式来讨论这些理论——即商业世界大多采用的"教堂"模式与 Linux 世界的"集市"模式。我展示了这两种模式源于对软件调试任务本质的对立假设。随后，我从 Linux 的经验出发，对"只要眼球足够多，所有 bug 都无处遁形"这一命题进行了系统的论证，提出了与其他由自利智能体组成的自我修正系统的有益类比，并在此基础上探讨了这一洞察对软件未来的深远影响。

<h2 id="catb">教堂与集市</h2>

Linux 是颠覆性的。谁能在五年前（1991年）想到，一个世界级的操作系统竟然能够如同变魔术一般，从散布在全球各地的数千名开发者的业余 hacking 中凝聚而成，而他们之间唯一的联系不过是 Internet 上纤细的纽带？

反正我没想到。当 Linux 在1993年初进入我的视野时，我已经在 Unix 和开源开发领域耕耘了十年。我是1980年代中期 GNU 项目的早期贡献者之一。我在网上发布了大量的开源软件，独立开发或参与开发了若干程序（nethack、Emacs 的 VC 和 GUD 模式、xlife 等），这些程序至今仍被广泛使用。我以为我知道这是怎么做到的。

Linux 推翻了我自以为知道的很多东西。多年来我一直在布道 Unix 的小工具、快速原型和演化式编程的福音。但我也相信存在某种临界复杂性，一旦超过它，就需要一种更加集中的、先验式的方法。我相信最重要的软件（操作系统和真正大型工具如 Emacs 编辑器）需要像教堂一样来建造，由个别高手或小群巫师在与世隔绝的环境中精心打造，不成熟绝不发布。

Linus Torvalds 的开发风格——尽早发布、频繁发布、能委托的就委托、开放到毫无保留的程度——让人大吃一惊。这里没有安静虔诚的教堂建造——相反，Linux 社区更像是一个喧闹的大集市，各种不同的议程和方法纷然并存（Linux 档案站点恰如其分地象征了这一点——它们接受任何人的投稿），一个连贯而稳定的系统竟然似乎只能通过一连串的奇迹从中浮现。

这种集市风格竟然行之有效，而且效果出色，这让人颇感震惊。在我逐步深入了解的过程中，我不仅在个别项目上努力工作，更在努力思考为什么 Linux 世界不仅没有陷入混乱而分崩离析，反而以一种让教堂建造者们几乎无法想象的速度不断增强。

到1996年年中，我觉得自己开始明白了。偶然的机会给了我一个完美的验证方式——一个开源项目，我可以有意识地尝试用集市模式来运作。我这样做了，而且取得了显著的成功。

这就是那个项目的故事。我将用它来提出一些关于高效开源开发的格言。并非所有这些都是我首次在 Linux 世界学到的，但我们将看到 Linux 世界如何赋予它们特别的意义。如果我是对的，它们将帮助你理解到底是什么使 Linux 社区成为优秀软件的源泉——而且，也许它们还能帮助你自身变得更加高效。

<h2 id="the-mail-must-get-through">邮件必须送达</h2>

自1993年起，我一直在宾夕法尼亚州西切斯特的一个名为 Chester County InterLink（CCIL）的小型免费 Internet 服务提供商那里负责技术方面的工作。我联合创办了 CCIL，并编写了我们独特的多用户公告板软件——你可以通过 telnet 连接到 [locke.ccil.org](telnet://locke.ccil.org) 来看看。如今它在三十条线路上支持近三千名用户。这份工作让我能够通过 CCIL 的 56K 专线每天24小时上网——事实上，这份工作本身就要求我这么做！

我已经非常习惯于即时的 Internet 电子邮件。我发现需要时不时地 telnet 到 locke 上去查收邮件令人烦恼。我希望的是让我的邮件直接投递到 snark（我的家用系统）上，这样邮件一到我就能收到通知，而且可以使用我所有的本地工具来处理。

Internet 原生的邮件转发协议 SMTP（简单邮件传输协议）并不合适，因为它在机器全天候连接时效果最佳，而我的个人机器并非总是在线，也没有固定的 IP 地址。我需要的是一个能够通过我时断时续的拨号连接去抓取邮件并在本地投递的程序。我知道这种东西是存在的，而且大多数使用一个叫做 POP（邮局协议）的简单应用协议。如今大多数常见邮件客户端都广泛支持 POP，但在当时，我使用的邮件阅读器并没有内置这个功能。

我需要一个 POP3 客户端。于是我到 Internet 上找了一个。实际上，我找到了三四个。我用了一段时间其中一个，但它缺少一个看起来很显而易见的功能——能够修改抓取到的邮件的地址，使得回复能够正常工作。

问题是这样的：假设 locke 上一个叫 'joe' 的人给我发了邮件。如果我把邮件抓到 snark 上然后尝试回复，我的邮件程序会高高兴兴地尝试把它发给 snark 上一个根本不存在的 'joe'。手动编辑回复地址加上 &lt;@ccil.org&gt; 很快就变成了一件令人头疼的事。

这显然应该是计算机替我做的事情。但现有的 POP 客户端没有一个知道该怎么做！这就引出了第一条经验：

> 1\. 每一个优秀的软件作品都始于开发者想要挠自己的痒。

也许这本应该是显而易见的（"需要是发明之母"这句谚语由来已久），但太多时候软件开发者每天都在为了报酬而磨洋工，开发着他们既不需要也不热爱的程序。但在 Linux 世界里不是这样——这也许可以解释为什么源自 Linux 社区的软件平均质量如此之高。

那么，我是否立刻投入到疯狂的编码中，从头写一个全新的 POP3 客户端来与现有的竞争？想得美！我仔细审视了手头的 POP 工具，问自己"哪一个最接近我想要的？"因为：

> 2\. 优秀的程序员知道该写什么。伟大的程序员知道该重写什么（以及复用什么）。

虽然我不敢自称伟大的程序员，但我努力效仿他们。伟大程序员的一个重要特质就是建设性的懒惰。他们知道你拿 A 不是因为努力而是因为成果，而且几乎总是从一个好的半成品开始比从零开始要容易得多。

例如，[Linus Torvalds](http://www.tuxedo.org/~esr/faqs/linus) 并没有真正尝试从零开始写 Linux。相反，他一开始复用了 Minix（一个用于 PC 的小型类 Unix 操作系统）的代码和思想。最终所有的 Minix 代码都消失或被完全重写了——但在它还在的时候，它为这个日后将成为 Linux 的婴儿提供了脚手架。

本着同样的精神，我去寻找一个编写得相当不错的现有 POP 工具，作为开发基础。

Unix 世界的源代码共享传统一直对代码复用很友好（这也是 GNU 项目选择 Unix 作为基础操作系统的原因，尽管对操作系统本身有严重的保留意见）。Linux 世界将这一传统几乎推到了技术极限；它有着数以 TB 计的普遍可用的开源代码。因此，在 Linux 世界里花时间寻找别人的差不多够好的代码，比在任何其他地方都更有可能给你带来好的结果。

对我而言确实如此。加上之前找到的，我的第二轮搜索总共凑出了九个候选——fetchpop、PopTart、get-mail、gwpop、pimp、pop-perl、popc、popmail 和 upop。我最初选定的是 Seung-Hong Oh 写的 'fetchpop'。我把我的信头重写功能加了进去，还做了其他各种改进，作者接受了并将它们纳入了他的 1.9 版本。

但几周后，我偶然发现了 Carl Harris 编写的 popclient 代码，发现我面临一个问题。虽然 fetchpop 有一些很好的原创想法（比如它的后台守护进程模式），但它只能处理 POP3，而且编码相当业余（Seung-Hong 当时是一个聪明但缺乏经验的程序员，两种特质都有所体现）。Carl 的代码更好，非常专业和稳健，但他的程序缺少几个重要的且相当棘手的 fetchpop 功能（包括我自己编码的那些）。

留下还是换船？如果换的话，我就要扔掉已经做过的编码，换取一个更好的开发基础。

切换的一个实际动机是多协议支持的存在。POP3 是最常用的邮局服务器协议，但不是唯一的一个。Fetchpop 和其他竞争者不支持 POP2、RPOP 或 APOP，而我已经在模糊地想着也许可以加上 [IMAP](http://www.imap.org/)（Internet 邮件访问协议，最新设计也是最强大的邮局协议）纯粹为了好玩。

但我还有一个更理论性的理由认为换船可能也是个好主意，这是我在 Linux 之前很久就学到的。

    <p>3. "计划抛弃一个；反正你也会的。"</p>
  </blockquote>
  <figcaption>Fred Brooks，《人月神话》，第11章</figcaption>

或者换句话说，你往往在第一次实现一个解决方案之后才真正理解问题。第二次也许你就知道得足够多来做对了。所以如果你想做对，准备好至少从头来过一次<sup><a href="#fnJB" id="refJB">[JB]</a></sup>。

好吧（我对自己说），对 fetchpop 的改动是我的第一次尝试。所以我换了。

1996年6月25日，我把第一批 popclient 补丁发给 Carl Harris 后，发现他之前基本上已经对 popclient 失去了兴趣。代码有些积灰，小 bug 悬而未决。我有很多改动要做，我们很快达成共识：合乎逻辑的做法是由我来接管这个程序。

不知不觉间，项目升级了。我不再只是考虑对现有的 POP 客户端做些小修补。我承担起了维护一整个程序的责任，而且我脑海中已经冒出了许多想法，我知道这些想法很可能会带来重大变化。

在一个鼓励代码共享的软件文化中，这是一个项目演进的自然方式。我在践行这一原则：

> 4\. 如果你的态度正确，有趣的问题自然会找上门来。

但 Carl Harris 的态度更为重要。他明白：

> 5\. 当你对一个程序失去兴趣时，你对它的最后一个责任就是把它交给一个称职的继任者。

无需讨论，Carl 和我都心知肚明，我们有一个共同的目标——让最好的解决方案面世。对我们俩任何一方来说，唯一的问题是我能否证明自己是一双可靠的手。一旦我证明了这一点，他就表现得优雅而果断。希望轮到我的时候，我也能做得同样好。

<h2 id="the-importance-of-having-users">拥有用户的重要性</h2>

就这样，我继承了 popclient。同样重要的是，我继承了 popclient 的用户群。用户是极好的东西，不仅仅因为他们证明你在满足某种需求、你做对了某些事。经过恰当的培育，他们可以成为共同开发者。

Unix 传统的另一个优势——Linux 将其推向了令人愉快的极端——是大量用户同时也是黑客。因为源代码是公开的，他们可以是_有实效的_黑客。这对缩短调试时间有着巨大的帮助。只要稍加鼓励，你的用户就会为你诊断问题、建议修复方案，并帮助改进代码，其速度远非你单枪匹马所能比拟。

> 6\. 把你的用户当作共同开发者，是快速改进代码和有效调试的最省心之道。

这种效应的力量很容易被低估。事实上，我们开源世界的几乎所有人都严重低估了它随用户数量和系统复杂性扩展的程度——直到 Linus Torvalds 用事实证明我们错了。

事实上，我认为 Linus 最聪明、最影响深远的 hack 不是 Linux 内核本身的构建，而是他发明的 Linux 开发模式。有一次当着他的面表达这个观点时，他微笑着平静地重复了一句他常说的话："我基本上是一个非常懒惰的人，喜欢把别人实际上做的事情归功于自己。"像狐狸一样懒惰。或者，正如 Robert Heinlein 在描述他笔下一个角色时著名地写到的那样：懒惰到不会失败。

回想起来，Linux 的方法和成功的一个先例可以在 GNU Emacs Lisp 库和 Lisp 代码档案的发展中看到。与 Emacs C 核心和大多数其他 GNU 工具的教堂建造风格形成对比，Lisp 代码池的演化是流动的、非常以用户驱动的。想法和原型模式在被重写三四次之后才达到稳定的最终形态。而且，借由 Internet 促成的松散耦合协作——_如同_ Linux 那样——是司空见惯的。

实际上，在 fetchmail 之前我个人最成功的 hack 可能就是 Emacs VC（版本控制）模式，这是一个类似 Linux 的通过电子邮件与另外三个人进行的协作，其中只有一位（Richard Stallman，Emacs 的作者和[自由软件基金会](http://www.fsf.org/)的创始人）我至今见过面。它是 Emacs 中 SCCS、RCC 和后来的 CVS 的前端，提供"一键式"版本控制操作。它是从别人写的一个简陋的 sccs.el 模式演化而来的。VC 的开发之所以成功，是因为不同于 Emacs 本身，Emacs Lisp 代码可以非常快速地经历发布/测试/改进的迭代。

Emacs 的故事并非独一无二。还有其他软件产品具有双层架构和双层用户社区，结合了教堂模式的核心和集市模式的工具箱。其中一个就是 MATLAB，一个商用的数据分析和可视化工具。MATLAB 和其他具有类似结构的产品的用户无一例外地报告说，那些行动、那些发酵、那些创新大部分发生在工具的开放部分，在那里一个庞大而多元的社区可以自由地修修补补。

<h2 id="release-early-release-often">早发布，勤发布</h2>

尽早且频繁地发布是 Linux 开发模式的关键部分。大多数开发者（包括我在内）过去都认为对于非平凡的项目来说这不是好策略，因为早期版本几乎注定是有 bug 的版本，而你不想耗尽用户的耐心。

这种信念加强了对教堂建造式开发的普遍承诺。如果首要目标是让用户看到尽可能少的 bug，那么你就每六个月（或更长时间）才发布一个版本，然后在两次发布之间拼命调试。Emacs 的 C 核心就是这样开发的。而 Lisp 库实际上不是——因为在 FSF 控制之外还有活跃的 Lisp 档案，你可以在那里独立于 Emacs 的发布周期找到新的和开发中的代码版本<sup><a href="#fnQR" id="refQR">[QR]</a></sup>。

其中最重要的一个是俄亥俄州立大学 Emacs Lisp 档案，它预示了今天大型 Linux 档案的精神和许多特征。但我们中几乎没有人真正认真思考过我们在做什么，或者那个档案的存在本身对 FSF 的教堂建造开发模式所暗示的问题。1992年前后，我曾认真地试图将大量俄亥俄的代码正式合并到官方的 Emacs Lisp 库中。但我遇到了政治上的麻烦，基本上没有成功。

但一年之后，随着 Linux 变得广为人知，很明显那里正在发生一些不同的、更健康的事情。Linus 的开放开发政策与教堂建造恰恰相反。Linux 的 Internet 档案蓬勃发展，多个发行版被推出。而这一切都是由一种闻所未闻的核心系统发布频率所推动的。

Linus 以最有效的方式把他的用户当作共同开发者：

> 7\. 早发布。勤发布。倾听你的客户。

Linus 的创新并不在于做了包含大量用户反馈的快速迭代发布（这种做法在 Unix 世界已有悠久的传统），而在于将其提升到了一种与他所开发的系统复杂性相匹配的强度。在那些早期（大约1991年），他一天发布一个以上的新内核都不稀奇！因为他精心培育自己的共同开发者基础，并且比任何人都更卖力地利用 Internet 进行协作，这奏效了。

但它_为什么_能奏效？这是我能够复制的，还是依赖于 Linus Torvalds 的某种独特天赋？

我不这么认为。诚然，Linus 是一个非常出色的黑客。我们中有多少人能从零开始构建一个生产级的操作系统内核？但 Linux 并不代表任何了不起的概念飞跃。Linus 并不是（或至少目前还不是）那种设计方面的创新天才，比如 Richard Stallman 或 James Gosling（NeWS 和 Java 的创造者）那种级别。相反，在我看来 Linus 是一个工程和实现方面的天才，有着避免 bug 和开发死胡同的第六感，以及找到从 A 点到 B 点最小努力路径的真正天赋。事实上，Linux 的整体设计散发着这种特质，映射出 Linus 本质上保守化和简化化的设计方法。

那么，如果快速发布和将 Internet 媒介利用到极致并非偶然，而是 Linus 的工程天才对最小努力路径的洞察的有机组成部分，那他在最大化什么？他从这台机器里 churn 出的是什么？

这样一问，问题便自明了。Linus 在不断地刺激和奖励他的黑客/用户——用参与令人自我满足的项目的_前景_来刺激他们，用他们的工作中持续的（甚至_每天_的）改进来奖励他们。

Linus 直接瞄准的是最大化投入调试和开发的人时数，甚至不惜以代码不稳定和用户群体疲劳为代价（如果某个严重的 bug 顽固不化的话）。Linus 的行为仿佛他相信这样的事情：

> 8\. 只要 beta 测试者和共同开发者基数足够大，几乎每个问题都会被迅速定位，而修复方案对某人来说是显而易见的。

或者，不那么正式地说："只要眼球足够多，所有 bug 都无处遁形。"我将其命名为："Linus 定律"。

我最初的表述是每个问题"对某人来说将是透明的"。Linus 表示反对，认为理解并修复问题的人不一定甚至通常不是最初发现问题的人。"有人发现问题，"他说，"另一个人_理解_它。而且我愿意公开说，发现问题是更大的挑战。"这个纠正很重要；我们将在下一节更详细地审视调试实践时看到它的重要性。但关键在于，过程的两个部分（发现和修复）往往都会迅速发生。

在 Linus 定律中，我认为蕴含着教堂建造模式和集市模式之间根本差异的核心。在教堂建造者的编程观中，bug 和开发问题是棘手的、隐蔽的、深层现象。需要少数专注的人经过数月的审视才能确信你已经把它们全部揪出来了。因此才有了漫长的发布间隔，以及期待已久的发布并不完美时不可避免的失望。

而在集市观中，相反，你假设 bug 通常是浅层现象——或者至少，当暴露给一千个急切的共同开发者对新版本的每一行代码穷追猛打时，它们很快就会变成浅层的。因此你频繁地发布以获得更多的修正，而作为一个有益的副作用，即使偶尔有拙劣的版本流出去，你的损失也更小。

就是这样。这就够了。如果"Linus 定律"是假的，那么任何像 Linux 内核这样复杂的系统——在同样多的人手下被 hack——都应该在某个时刻被不可预见的恶性交互和未发现的"深层" bug 的重量所压垮。另一方面，如果它是真的，那就足以解释 Linux 相对缺少 bug 以及它连续运行数月甚至数年的持续正常运行时间。

也许这本不应该如此令人惊讶。社会学家多年前就发现，大量同等专业（或同等无知）的观察者的平均意见，比随机选取的单一观察者的意见要可靠得多。他们称之为德尔菲效应。看来 Linus 所展示的是，这甚至适用于调试操作系统——德尔菲效应即使在操作系统内核的复杂度水平上也能驯服开发复杂性。<sup><a href="#fnCV" id="refCV">[CV]</a></sup>

Linux 情况中一个显然有助于德尔菲效应发挥的特殊特征是，任何给定项目的贡献者都是自我筛选的。一位早期回应者指出，收到的贡献并非来自随机样本，而是来自那些对使用软件有足够兴趣、愿意学习其工作原理、试图解决遇到的问题并真正产生了看似合理的修复方案的人。任何通过了所有这些筛选的人，极可能有有用的东西可以贡献。

Linus 定律可以重新表述为"调试是可以并行化的"。虽然调试需要调试者与某个协调开发者进行沟通，但它不需要调试者之间进行显著的协调。因此它不会落入
同样会使添加开发者变得棘手的二次方复杂度和管理成本。

在实践中，由于调试者工作重复而导致的理论效率损失在 Linux 世界中似乎几乎不成问题。"早发布、勤发布"策略的一个效果就是通过快速传播反馈修复来最小化这种重复<sup><a href="#fnJH" id="refJH">[JH]</a></sup>。

Brooks（《人月神话》的作者）甚至做了一个与此相关的随口评论："维护一个广泛使用的程序的总成本通常是开发成本的40%或更多。令人惊讶的是，这个成本受用户数量的强烈影响。_更多的用户发现更多的bug。_"[斜体为原文所加]。

更多的用户发现更多的bug，因为增加用户就增加了对程序施压的不同方式。当用户也是共同开发者时，这种效应会被放大。每个人都以略微不同的感知方式和分析工具、不同的角度来看待bug特征化这个任务。"Delphi效应"似乎恰恰因为这种差异性而起作用。在调试的具体语境中，这种差异也倾向于减少重复劳动。

因此，增加更多的beta测试者也许不能从_开发者_的视角降低当前"最深"bug的复杂度，但它增加了概率，使得某个人的工具箱恰好匹配这个问题，从而让这个bug对_那个人_来说是浅显的。

Linus 也做了双重保险。万一_确实_存在严重的bug，Linux 内核版本的编号方式使得潜在用户可以选择运行上一个被标记为"稳定"的版本，或者冒险使用前沿版本以获取新功能。这种策略尚未被大多数 Linux 黑客系统地仿效，但也许应该如此；两种选择都可用这一事实使两者都更具吸引力。<sup><a href="#fnHBS" id="refHBS">[HBS]</a></sup>

<h2 id="how-many-eyeballs-tame-complexity">多少双眼睛才能驯服复杂性</h2>

从宏观上观察到集市风格大大加速了调试和代码演化是一回事。从微观层面——即开发者和测试者日常行为——理解它究竟如何以及为何如此，又是另一回事。在本节中（写于原文发表三年之后，借鉴了读过本文并重新审视自身行为的开发者们的洞见），我们将认真审视实际的机制。非技术背景的读者可以安全地跳到下一节。

理解的一个关键是要确切认识到，不了解源代码的用户通常提交的那种bug报告为什么往往不太有用。不了解源代码的用户倾向于只报告表面症状；他们将自身环境视为理所当然，因此他们(a)省略了关键的背景数据，(b)很少包含可靠的bug重现步骤。

这里的根本问题是测试者和开发者对程序的心智模型之间的不匹配——测试者从外向里看，而开发者从里向外看。在闭源开发中，他们都被困在各自的角色里，倾向于各说各话，并觉得对方令人深感沮丧。

开源开发打破了这一僵局，使测试者和开发者能够基于实际源代码建立起共享的表征，并围绕它进行有效沟通。在实践中，对于开发者来说，仅仅报告外部可见症状的bug报告与直接对接到开发者基于源代码的心智表征的bug报告之间，存在着巨大的杠杆差异。

大多数bug，在大多数时候，只要对错误条件有一个哪怕不完整但具有启发性的源代码层面描述，就能轻松解决。当你的beta测试者中有人能指出"第nnn行有个边界问题"，或者哪怕只是"在X、Y和Z条件下，这个变量溢出了"，快速查看相关代码往往就足以确定故障的确切模式并生成修复方案。

因此，双方对源代码的认知极大地促进了良好的沟通，以及beta测试者所报告内容与核心开发者所掌握内容之间的协同。反过来，这意味着核心开发者的时间能得到很好的节约，即使合作者众多。

开源方法节约开发者时间的另一个特征是典型开源项目的沟通结构。上面我使用了"核心开发者"这个术语；这反映了一个区分，即项目核心（通常非常小；单个核心开发者很常见，一到三人是典型的）与项目外围的beta测试者和可用贡献者（通常数以百计）之间的区分。

传统软件开发组织所解决的根本问题是Brooks定律："为一个延期的项目增加更多程序员只会让它更加延期。"更一般地说，Brooks定律预言，项目的复杂度和沟通成本随开发者数量的平方增长，而完成的工作只是线性增长。

Brooks定律建立在一个经验观察之上：bug强烈倾向于聚集在不同人编写的代码之间的接口处，而项目中的沟通/协调开销倾向于随人际接口数量的增加而增长。因此，问题随开发者之间沟通路径的数量而扩展，而沟通路径数量随开发者数量的平方增长（更精确地说，按照公式 N\*(N - 1)/2，其中N是开发者数量）。

Brooks定律的分析（以及对开发组人数过多的担忧）建立在一个隐含假设之上：即项目的沟通结构必然是一个完全图，每个人都与其他每个人交流。但在开源项目中，外围开发者实际上在做的是可分离的并行子任务，彼此之间很少互动；代码变更和bug报告通过核心组流转，只有在那个小小的核心组内部，我们才支付完整的Brooks式开销。<sup><a href="#fnSU" id="refSU">[SU]</a></sup>

源代码层面的bug报告之所以如此高效，还有更多的原因。它们围绕这样一个事实：单个错误通常可以有多个可能的症状，根据用户使用模式和环境的细节而表现得不同。这类错误往往恰好是那种复杂而微妙的bug（比如动态内存管理错误或非确定性的中断窗口伪影），它们最难随意重现或通过静态分析来定位，也最容易给软件造成长期问题。

一个测试者如果提交了这种多症状bug的试探性源代码层面描述（例如"在我看来，1250行附近的信号处理有个时间窗口"或者"你在哪里给那个缓冲区清零的？"），可能会给一个离代码太近反而看不清问题的开发者提供关键线索，从而解开好几个看似无关的症状。在这种情况下，可能很难甚至不可能知道哪个外部可见的错误行为恰好由哪个bug引起——但凭借频繁的发布，这并不必要。其他合作者很可能很快发现他们的bug是否已被修复。在许多情况下，源代码层面的bug报告会让错误行为悄然消失，而无需归因于任何具体的修复。

复杂的多症状错误还具有从表面症状回溯到实际bug的多条追踪路径这一特点。某个开发者或测试者能够追踪哪条路径，可能取决于该人员环境的微妙因素，并且可能以一种不太明显具有确定性的方式随时间变化。实际上，每个开发者和测试者在寻找某个症状的病因时，都在对程序状态空间进行半随机的采样。bug越微妙越复杂，技能就越难以保证采样的相关性。

因此，对于简单且容易重现的bug，重点在"半"而非"随机"——调试技能和对代码及其架构的熟悉程度将非常重要。但对于复杂的bug，重点在"随机"。在这种情况下，许多人同时运行追踪比少数人依次运行追踪要有效得多——即使少数人的平均技能水平高得多。

如果从不同表面症状回溯到某个bug的追踪路径难度差异很大，且这种差异无法通过观察症状来预测，那么上述效应将被大大放大。单个开发者依次采样这些路径时，第一次尝试选到困难路径和选到容易路径的可能性一样大。另一方面，假设许多人在快速发布的同时并行尝试各种追踪路径，那么他们中的某个人很可能会立即发现最容易的路径，并在短得多的时间内搞定这个bug。项目维护者会看到这一点，发布一个新版本，而其他正在追踪同一个bug的人就能在各自的困难路径上花费太多时间之前停下来<sup><a href="#fnRJ" id="refRJ">[RJ]</a></sup>。

<h2 id="when-is-a-rose-not-a-rose">何时玫瑰不是玫瑰？</h2>

在研究了 Linus 的行为并形成了关于其成功原因的理论之后，我有意识地决定在我自己的新项目上（诚然远不如 Linux 复杂和雄心勃勃）测试这个理论。

但我做的第一件事是大规模地重组和简化 popclient。Carl Harris 的实现非常扎实，但表现出许多 C 程序员共有的一种不必要的复杂性。他将代码视为核心，将数据结构视为代码的辅助。结果，代码很漂亮，但数据结构设计是临时的且相当丑陋（至少以这位老牌 LISP 黑客的高标准来看）。

除了改进代码和数据结构设计之外，我重写还有另一个目的。那就是将其演化成我完全理解的东西。负责修复一个你自己都不理解的程序中的bug，绝非乐事。

因此，在最初的一个月左右，我只是在推演 Carl 基本设计的含义。我做出的第一个重大改变是添加 IMAP 支持。我通过将协议机重组为一个通用驱动器和三个方法表（分别用于 POP2、POP3 和 IMAP）来实现这一点。这一改变和之前的改变都阐明了一个程序员最好铭记在心的一般原则，尤其是在 C 这种不做动态类型检查的语言中：

> 9\. 聪明的数据结构和笨拙的代码，远比反过来要好得多。

Brooks，第9章："给我看你的流程图而藏起你的表，我将继续迷惑不解。给我看你的表，我通常不需要你的流程图；它将不言自明。"考虑到三十年的术语/文化变迁，这是同一个观点。

在这个时候（1996年9月初，从零开始大约六周），我开始考虑可能需要更改名字了——毕竟，它已经不再只是一个 POP 客户端了。但我犹豫了，因为设计中还没有出现真正新颖的东西。我的 popclient 版本尚未发展出自己的身份。

当 popclient 学会了如何将获取的邮件转发到 SMTP 端口时，一切都彻底改变了。我稍后会谈到这一点。但首先：我之前说过我决定用这个项目来测试我关于 Linus Torvalds 做对了什么的理论。我（你可能要问）是怎么做的呢？通过以下方式：

- 我早发布、勤发布（几乎从不少于每十天一次；在密集开发期间，每天一次）。
- 我通过将每个联系我关于 fetchmail 的人加入来扩大我的 beta 列表。
- 每次发布时我都向 beta 列表发送生动的公告，鼓励人们参与。
- 我倾听我的 beta 测试者，就设计决策征求他们的意见，并在他们提交补丁和反馈时给予赞扬。

这些简单措施的回报立竿见影。从项目的最开始，我就得到了大多数开发者梦寐以求的高质量bug报告，通常还附带了优秀的修复方案。我得到了深思熟虑的批评、粉丝来信、聪明的功能建议。这引出了：

> 10\. 如果你把你的beta测试者当作你最宝贵的资源来对待，他们就会通过成为你最宝贵的资源来回应。

fetchmail 成功的一个有趣的衡量标准是项目 beta 列表 fetchmail-friends 的庞大规模。在本文最近一次修订时（2000年11月），它有287名成员，并且每周增加两到三个。

实际上，当我在1997年5月下旬修订时，我发现列表开始从接近300人的高点流失成员，原因是颇为有趣的。有几个人要求我退订他们，因为 fetchmail 为他们工作得如此之好，以至于他们不再需要看到列表流量！也许这是成熟的集市风格项目正常生命周期的一部分。

<h2 id="popclient-becomes-fetchmail">Popclient 变身 Fetchmail</h2>

项目的真正转折点是 Harry Hochheiser 发给我他的草稿代码，用于将邮件转发到客户端机器的 SMTP 端口。我几乎立刻意识到，这个功能的一个可靠实现将使所有其他邮件传递模式变得近乎过时。

许多周以来，我一直在相当渐进地调整 fetchmail，同时感觉界面设计虽然可用但很粗糙——不优雅，而且有太多细瘦的选项到处悬挂。将获取的邮件转储到邮箱文件或标准输出的选项特别让我困扰，但我又说不出为什么。

（如果你不关心互联网邮件的技术细节，接下来的两段可以安全跳过。）

当我思考 SMTP 转发时，我看到的是 popclient 一直在试图做太多的事情。它被设计成同时充当邮件传输代理（MTA）和本地投递代理（MDA）。有了 SMTP 转发，它就可以退出 MDA 的业务，成为一个纯粹的 MTA，像 sendmail 那样将邮件交给其他程序进行本地投递。

既然端口25几乎可以保证在任何支持 TCP/IP 的平台上都存在，为什么还要费心配置邮件投递代理的所有复杂性，或者在邮箱上设置锁定和追加操作呢？尤其是这意味着取回的邮件保证看起来像正常的发件人发起的 SMTP 邮件，而这恰恰是我们想要的。

（回到更高的层面......）

即使你没有理解前面的技术术语，这里也有几个重要的教训。首先，这个 SMTP 转发概念是我有意识地尝试效仿 Linus 的方法所获得的最大单项回报。一个用户给了我这个绝妙的想法——我要做的只是理解其含义。

> 11\. 仅次于自己有好主意的是识别来自用户的好主意。有时候后者更好。

有趣的是，你很快就会发现，如果你完全且自嘲般地坦诚你欠了别人多少，世人反而会把你当作所有发明都是你一个人做的，你只是对与生俱来的天才表现得恰如其分地谦虚。我们都能看到这对 Linus 来说效果多么好！

（当我在1997年8月的第一次 Perl 大会上做演讲时，黑客中的佼佼者 Larry Wall 就坐在前排。当我读到上面最后一行时，他以宗教复兴集会的风格喊道："说出来，说出来，兄弟！"全场哄堂大笑，因为他们知道这对 Perl 的发明者也同样奏效。）

以同样的精神运营项目仅仅几周后，我开始收到类似的赞誉——不仅来自我的用户，还来自消息泄露出去后的其他人。我保存了一些这样的电子邮件；如果有一天我开始怀疑自己的人生是否有意义，我会再拿出来看看 :-)。

但这里还有两个更根本的、与政治无关的、适用于所有类型设计的教训。

> 12\. 通常，最引人注目和最创新的解决方案来自于你意识到自己对问题的概念是错误的。

我一直在试图解决错误的问题——继续将 popclient 开发为一个带有各种花哨本地投递模式的 MTA/MDA 混合体。Fetchmail 的设计需要从头重新思考，作为一个纯粹的 MTA，正常的会说 SMTP 的互联网邮件路径的一部分。

当你在开发中碰壁——当你发现自己很难想到下一个补丁之后的事情时——这通常是你该问的不是你是否得到了正确的答案，而是你是否在问正确的问题的时候了。也许问题需要被重新框定。

好吧，我重新框定了我的问题。显然，正确的做法是 (1) 将 SMTP 转发支持加入通用驱动器，(2) 使其成为默认模式，(3) 最终抛弃所有其他投递模式，尤其是投递到文件和投递到标准输出的选项。

我在第3步上犹豫了一段时间，担心会 upsetting 依赖于替代投递机制的老 popclient 用户。理论上，他们可以立即转用 .forward 文件或其非 sendmail 等效物来达到同样的效果。但实际上过渡可能会很混乱。

但当我真的这么做了，好处是巨大的。驱动器代码中最破旧的部分消失了。配置变得极其简单——不再需要为系统 MDA 和用户邮箱四处翻找，不再需要担心底层操作系统是否支持文件锁定。

同时，丢失邮件的唯一途径也消失了。如果你指定了投递到文件而磁盘满了，你的邮件就会丢失。而 SMTP 转发不会出现这种情况，因为你的 SMTP 监听器不会返回 OK，除非消息可以被投递或至少被排队等待稍后投递。

此外，性能也提高了（虽然单次运行中你注意不到）。这个变化的另一个不无益处的好处是手册页变得简单多了。

后来，我不得不将用户指定的本地 MDA 投递方式重新引入，以处理涉及动态 SLIP 的一些冷门情况。但我找到了一种简单得多的方式来做到这一点。

教训是什么？当你能够在不损失效力的前提下做到时，不要犹豫扔掉过时的功能。Antoine de Saint-Exupéry（当他不是在创作经典儿童文学时，他是一名飞行员和飞机设计师）说过：

> 13\. "完美（在设计上）不是当没有什么可以再添加的时候达到的，而是当没有什么可以再删去的时候达到的。"

当你的代码同时变得更好和更简单时，你就_知道_它是对的了。在这个过程中，fetchmail 的设计获得了自己的身份，不同于其前身 popclient。

是时候改名了。新设计看起来比旧的 popclient 更像是 sendmail 的对偶——两者都是 MTA，但 sendmail 是先推送再投递，而新的 popclient 是先拉取再投递。因此，在启动两个月后，我将其更名为 fetchmail。

关于 SMTP 投递是如何来到 fetchmail 的这个故事中，还有一个更一般的教训。不仅可以并行化调试；开发和对设计空间的探索（在令人惊讶的程度上）也是可以并行化的。当你的开发模式是快速迭代时，开发和增强可能成为调试的特殊形式——修复原始功能或软件概念中的"遗漏之bug"。

即使在更高的设计层面，让许多共同开发者在你的产品附近的设计空间中进行随机游走，也可能是非常有价值的。想想一滩水如何找到排水口，或者更好的例子——蚂蚁如何找到食物：本质上是通过扩散来探索，然后通过可扩展的沟通机制来利用。这非常有效；就像 Harry Hochheiser 和我一样，你的某个前哨很可能在附近找到一个巨大的收获，而你只因过于聚焦而未能看到。

<h2 id="fetchmail-grows-up">Fetchmail 茁壮成长</h2>

我就这样拥有了一个精巧而创新的设计，一份我知道运行良好的代码（因为我每天都在使用），以及一个不断壮大的 beta 列表。我逐渐意识到，我不再只是在做一个碰巧对其他几个人有用的个人小项目。我手中握着一个每个拥有 Unix 机器和 SLIP/PPP 邮件连接的黑客都真正需要的程序。

凭借 SMTP 转发功能，它遥遥领先于竞争对手，有可能成为一个"品类杀手"——那种经典程序，它如此称职地填满了自己的生态位，以至于替代方案不仅被丢弃，而且几乎被遗忘。

我认为你无法真正瞄准或计划这样的结果。你必须被设计理念的力量所牵引，以至于事后看来结果似乎是必然的、自然的、甚至命中注定的。寻求这种理念的唯一方式是拥有大量的想法——或者拥有工程判断力，将他人的好想法推到原创者认为可以达到的地方之外。

Andy Tanenbaum 最初的想法是为 IBM PC 构建一个简单的原生 Unix，用作教学工具（他称之为 Minix）。Linus Torvalds 将 Minix 的概念推到了 Andrew 可能认为可以达到的地方之外——它成长为了一种了不起的东西。同样的道理（尽管规模较小），我采用了 Carl Harris 和 Harry Hochheiser 的一些想法，并将其大力推进。我们两人都不是以人们心目中天才的浪漫方式做到"原创"的。然而，大多数科学、工程和软件开发都不是由原创天才完成的，不管黑客神话如何言之凿凿地声称相反。

尽管如此，这些结果仍然颇为令人振奋——事实上，正是每个黑客为之而活的那种成功！而它们意味着我必须将标准提得更高。为了让 fetchmail 达到我现在看到它可以达到的水平，我不仅要为自己的需求而编写，还要包含和支持他人需要但在我的需求范围之外的功能。同时在保持程序简单和健壮的前提下做到这一点。

在认识到这一点之后，我编写的第一个也是压倒性地最重要的功能是多投（multidrop）支持——即从一个为整组用户累积了所有邮件的邮箱中获取邮件，然后将每封邮件路由到各自的收件人。

我决定添加多投支持，部分原因是一些用户在呼吁它，但主要原因是我认为它会通过迫使我全面处理地址问题，来将单投代码中的bug清除出来。事实证明确实如此。正确实现 [RFC 822](http://info.internet.isi.edu/in-notes/rfc/files/rfc822.txt) 地址解析花了我很长时间，不是因为任何单独的部分很难，而是因为它涉及一大堆相互依赖的琐碎细节。

但多投地址处理结果证明也是一个出色的设计决策。以下是我如何知道的：

> 14\. 任何工具都应该在预期的方式中有用，但一个真正伟大的工具会适用于你从未预料到的用途。

多投 fetchmail 的意外用途是运行邮件列表，而列表的维护和别名扩展都在互联网连接的客户端完成。这意味着通过 ISP 账户运行个人机器的人可以管理邮件列表，而无需持续访问 ISP 的别名文件。

我的 beta 测试者要求的另一个重要变化是支持 8 位 MIME（多用途互联网邮件扩展）操作。这相当容易做到，因为我一直小心保持代码的 8 位纯净（即不利用 ASCII 字符集中未使用的第8位来在程序内部携带信息）。不是因为我在预期到对这个功能的需求，而是遵循另一条规则：

> 15\. 在编写网关软
何种类型的转换，都要尽力不去干扰数据流——而且_绝不_丢弃信息，除非接收方迫使你这么做！

如果我当初没有遵守这条规则，8-bit MIME 支持就会变得既困难又充满 bug。实际上，我所要做的不过是阅读 MIME 标准（[RFC 1652](http://info.internet.isi.edu/in-notes/rfc/files/rfc1652.txt)），然后加上一小段生成头部信息的逻辑。

一些欧洲用户缠着我，要我加一个选项来限制每次会话获取的邮件数量（这样他们就能控制昂贵的电话网络费用）。我抵制了很久，到现在也不是完全满意。但如果你是为全世界写软件，你就得倾听用户的呼声——这一点不会因为他们没有付钱给你而改变。

<h2 id="a-few-more-lessons-from-fetchmail">从 Fetchmail 中得到的更多经验</h2>

在回到通用的软件工程问题之前，还有一些从 fetchmail 经验中得出的更具体的教训值得深思。非技术读者可以放心跳过本节。

rc（控制）文件语法包含可选的"噪声"关键词，这些关键词会被解析器完全忽略。它们所允许的类英语语法，比传统的那种把所有冗余去掉后得到的简洁关键词-值对，可读性要好得多。

这些最初是我深夜实验的产物，当时我注意到 rc 文件中的声明越来越像一种命令式迷你语言。（这也是为什么我把原来 popclient 的 "server" 关键词改成了 "poll"。）

我觉得，尝试让这种命令式迷你语言更像英语，可能会让它更容易使用。现在，虽然我是"把它做成一门语言"这一设计流派的坚定拥趸——Emacs、HTML 和许多数据库引擎都是这方面的典范——但我通常并不太热衷于"类英语"语法。

传统上，程序员倾向于偏好非常精确、紧凑、完全没有冗余的控制语法。这是一种文化遗留，源于计算资源昂贵的年代，因此解析阶段必须尽可能廉价和简单。英语有大约 50% 的冗余，在当时看来是一个非常不合适的模型。

这并不是我通常回避类英语语法的原因；我提到它只是为了先将其驳倒。在计算周期和内存都很便宜的今天，简洁不应成为目的本身。如今，一门语言对人类来说方便与否，远比对计算机来说便宜与否重要得多。

然而，仍然有充分的理由保持警惕。一个是解析阶段的复杂性成本——你不会想把它提高到本身就成了 bug 和用户困惑重要来源的程度。另一个是，试图让一门语言的语法像英语，往往需要严重扭曲所说的"英语"，以至于它与自然语言的表面相似性反而会和传统语法一样令人困惑。（你在许多所谓的"第四代"和商业数据库查询语言中都能看到这种不良效果。）

fetchmail 的控制语法似乎避免了这些问题，因为语言领域极其受限。它远非通用语言；它所表达的内容实在不太复杂，所以在脑海中切换于英语的一个小子集和实际控制语言之间时，几乎不会产生混淆。我觉得这里可能有一个更广泛的教训：

> 16. 当你的语言远非图灵完备时，语法糖可以是你的朋友。

另一个教训是关于"靠隐蔽来保证安全"（security by obscurity）。一些 fetchmail 用户要求我修改软件，将密码以加密形式存储在 rc 文件中，这样窥探者就无法随意看到密码。

我没有这样做，因为这实际上并不能增加保护。任何获得了读取你 rc 文件权限的人，反正都能以你的身份运行 fetchmail——如果他们想要的是你的密码，他们完全可以从 fetchmail 的代码中提取出必要的解码器来获取密码。

`.fetchmailrc` 的密码加密唯一能做到的，就是给那些不愿深入思考的人一种虚假的安全感。这里的一般规则是：

> 17. 一个安全系统的安全性取决于其秘密。当心伪秘密。

<h2 id="necessary-preconditions-for-the-bazaar-style">集市模式的必要前提</h2>

本文的早期审阅者和测试受众一致提出了关于成功的集市模式开发前提条件的问题，包括项目负责人的资质，以及在公开代码并开始尝试构建共同开发者社区时，代码应处于什么状态。

相当明显的是，一个人无法从一开始就以集市模式进行编码<sup><a href="#fnIN" id="refIN">[IN]</a></sup>。你可以用集市模式来测试、调试和改进，但要以集市模式来_发起_一个项目会非常困难。Linus 没有尝试过。我也没有。你初生的开发者社区需要有某种可运行、可测试的东西来把玩。

当你开始社区建设时，你需要能够展示的是一个_可信的承诺_。你的程序不必运行得特别好。它可以是粗糙的、有 bug 的、不完整的、文档匮乏的。但它绝不能做不到的是：(a) 能运行，(b) 让潜在的共同开发者相信，在可预见的未来它能被发展成一个非常酷的东西。

Linux 和 fetchmail 在公开发布时都有着强大而吸引人的基本设计。许多人在思考我所阐述的集市模式时，正确地考虑到了这一点至关重要，然后由此跳跃到了一个结论：项目领导者必须具备高度的设计直觉和聪明才智。

但 Linus 的设计源自 Unix。我的设计最初源自其前身 popclient（虽然后来它有了很大的变化，按比例来说比 Linux 的变化大得多）。那么，一个集市式项目的领导者/协调者真的必须具备 exceptional 的设计天赋吗，还是说他可以借助他人的设计天赋来应付？

我认为协调者是否能够原创出 exceptional 出色的设计并不关键，但协调者_能够从他人那里识别出好的设计想法_绝对至关重要。

Linux 和 fetchmail 项目都有这方面的证据。Linus 虽然不是（如前所述）一个惊艳的原创设计者，但展现了识别优秀设计并将其整合进 Linux 内核的强大能力。而我已经描述过 fetchmail 中最强大的设计理念（SMTP 转发）是如何来自其他人的。

本文的早期受众恭维我，说我在评估集市项目中的设计原创性时可能低估了它的重要性，因为我自己在这方面能力很强，因此习以为常了。这也许有些道理；设计（相对于编码或调试而言）确实是我最强的技能。

但在软件设计中表现得聪明和原创的问题在于，这会变成一种习惯——当你应该保持健壮和简单时，你会本能地把东西做得花哨而复杂。我就有过因为犯了这个错误而导致项目失败的经历，但我设法在 fetchmail 上避免了这个错误。

因此我相信 fetchmail 项目之所以成功，部分原因正是我克制了自己卖弄聪明的倾向；这至少反驳了"设计原创性对成功的集市项目必不可少"这一观点。再看看 Linux。假设 Linus Torvalds 在开发过程中试图在操作系统设计上实现根本性的创新；那么最终生成的内核是否还能像我们现在拥有的这样稳定和成功，看起来还有可能吗？

当然，需要有一定基本水平的设计和编码技能，但我预计几乎任何认真考虑发起集市式开发的人都已经超过这个最低要求。开源社区以声誉为核心的内部市场会对人们施加微妙的压力，使他们不会发起自己无力完成的开发工作。到目前为止，这似乎运作得相当好。

还有一种通常不与软件开发联系在一起的技能，我认为它对集市项目而言与设计聪明才智同等重要——甚至可能更重要。一个集市项目的协调者或领导者必须具备良好的人际交往和沟通技能。

这应该是显而易见的。为了建立一个开发社区，你需要吸引人们，让他们对你正在做的事情产生兴趣，并让他们对所做的工作量感到满意。技术上的亮点能在这方面帮你大忙，但这远不是全部。你所展现出的个性同样重要。

Linus 是一个让人们喜欢他并愿意帮助他的好人，这并非巧合。我是一个精力充沛的外向者，喜欢在人群中游刃有余，有着一些类似脱口秀演员的表达方式和直觉，这也并非巧合。要让集市模式发挥作用，如果你至少有一点讨人喜欢的魅力，那将有极大的帮助。

<h2 id="the-social-context-of-open-source-software">开源软件的社会环境</h2>

有言道：最优秀的 hack 最初都是为了解决作者自己日常问题的个人方案，后来之所以传播开来，是因为这个问题结果证明对一大类用户来说都很典型。这让我们回到了规则 1，以一种或许更有用的方式重新表述：

> 18. 要解决一个有趣的问题，先找到一个对你来说有趣的问题。

Carl Harris 和其前身 popclient 如此，我和 fetchmail 亦然。但这一点早已为人所知。有趣的要点——Linux 和 fetchmail 的历史似乎要求我们关注的要点——是下一个阶段：在大量活跃的用户和共同开发者社区存在的情况下，软件的演进。

在《人月神话》（_The Mythical Man-Month_）中，Fred Brooks 观察到程序员的时间是不可替代的；为一个延期的软件项目增加开发者只会让它更加延期。正如我们前面所见，他认为一个项目的复杂性和沟通成本随开发者数量的平方增长，而完成的工作量只是线性增长。Brooks 定律被广泛视为不证自明的真理。但我们在本文中考察了多种方式，表明开源开发过程证伪了其背后的假设——而且从经验上看，如果 Brooks 定律就是全部真相，那么 Linux 是不可能存在的。

Gerald Weinberg 的经典著作《计算机编程心理学》（_The Psychology of Computer Programming_）提供了我们在事后看来对 Brooks 的重要修正。在他对"无我编程"（egoless programming）的讨论中，Weinberg 观察到，在那些开发者不对自己的代码抱有领地意识、并鼓励他人寻找 bug 和潜在改进的团队中，改进发生的速度比其他地方快得多。（最近，Kent Beck 的"极限编程"技术中让程序员成对工作、互相查看对方代码的做法，可以被视为一种试图强制产生这种效果的努力。）

Weinberg 的术语选择也许阻碍了他的分析获得应有的认可——想到把 Internet 黑客描述为"无我的"就让人不禁微笑。但我认为他的论点在今天看来比以往任何时候都更有说服力。

集市方法通过充分利用"无我编程"效应，有力地缓解了 Brooks 定律的影响。Brooks 定律背后的原理并没有被推翻，但在大量开发者群体和廉价通信的条件下，其效应可以被其他不可见的竞争性非线性因素所淹没。这类似于牛顿物理学与爱因斯坦物理学之间的关系——旧的体系在低能量状态下仍然有效，但如果你把质量和速度推得足够高，你就会得到核爆炸或 Linux 这样的惊喜。

Unix 的历史本应为我们从 Linux 中所学到的做好准备（我也通过刻意模仿 Linus 的方法在较小规模上进行了实验验证<sup><a href="#fnEGCS" id="refEGCS">[EGCS]</a></sup>）。也就是说，虽然编程本质上仍然是一项 solitary 的活动，但真正伟大的 hack 来自于调动整个社区的注意力和脑力。在一个封闭项目中只使用自己大脑的开发者，将会落后于那些知道如何创造一个开放的、进化式的环境的开发者——在这种环境中，对设计空间的探索反馈、代码贡献、bug 发现和其他改进来自数百（也许数千）人。

但传统的 Unix 世界由于几个因素而未能将这种方法推向极致。一个是各种许可证、商业秘密和商业利益的法律约束。另一个（事后看来）是当时的 Internet 还不够好。

在廉价的 Internet 出现之前，确实存在一些地理上紧凑的社区，那里的文化鼓励 Weinberg 所说的"无我"编程，一个开发者可以很容易地吸引大量有能力的旁观者和共同开发者。Bell Labs、MIT 的 AI 和 LCS 实验室、UC Berkeley——这些地方成为了传奇般且至今仍充满活力的创新的发源地。

Linux 是第一个有意识地并成功地将整个_世界_作为人才库的项目。我不认为 Linux 的孕育期与万维网的诞生恰好重合是巧合——Linux 正是在 1993—1994 年 ISP 行业起飞、主流社会对 Internet 兴趣爆发的同一时期走出了婴儿期。Linus 是第一个学会按照 Internet 普及所带来的新规则来玩这场游戏的人。

虽然廉价的 Internet 是 Linux 模式演进的必要条件，但我认为它本身并不是充分条件。另一个至关重要的因素是发展出一种领导风格和一套合作规范，使得开发者能够吸引共同开发者并从这一媒介中获得最大的杠杆效应。

但这种领导风格是什么？这些规范又是什么？它们不能建立在权力关系之上——即使可以，靠强制来领导也不会产生我们所看到的结果。Weinberg 引用了 19 世纪俄罗斯无政府主义者 Pyotr Alexeyvich Kropotkin 的自传《一个革命者的回忆》（_Memoirs of a Revolutionist_）中对此话题的精彩论述：

> 我在一个农奴主家庭中长大，步入社会生活时，和当时所有年轻人一样，对发号施令、下令、训斥、惩罚之类的事充满信心。但当我在早期就不得不管理重要的事务，并与自由人打交道时，当每一个失误都会立即导致严重后果时，我开始体会到基于命令和纪律的原则行事，与基于共同理解的原则行事之间的巨大差异。前者在军事阅兵中表现出色，但在涉及真实生活、且目标只能通过许多汇聚的意志的严肃努力才能实现时，它就一文不值了。

"许多汇聚的意志的严肃努力"正是一个像 Linux 这样的项目所需要的——而"命令的原则"在我们称之为 Internet 的无政府主义天堂中的志愿者之间实际上是无法实施的。为了有效地运作和竞争，想要领导协作项目的黑客必须学会如何按照 Kropotkin 的"理解的原则"所模糊暗示的模式来招募和激活有效的兴趣社区。他们必须学会运用 Linus 定律。<sup><a href="#fnSP" id="refSP">[SP]</a></sup>

之前我曾将"德尔菲效应"作为 Linus 定律的一种可能解释。但与生物学和经济学中自适应系统更有力的类比也不由自主地浮现出来。Linux 世界在许多方面的行为就像一个自由市场或一个生态系统，一个由自私的个体组成的集合试图最大化自身效用，而在这个过程中产生了一种自我修正的自发秩序，其精巧和高效程度是任何中央计划都无法企及的。因此，我们应该在这里寻找"理解的原则"。

Linux 黑客们正在最大化的"效用函数"不是经典意义上的经济学函数，而是他们自身 ego 的满足感和在其他黑客中的声誉这一无形之物。（人们可以说他们的动机是"利他的"，但这忽略了利他主义本身对利他者而言就是一种 ego 满足形式。）以这种方式运作的自愿性文化实际上并不罕见；另一个我长期参与的是科幻小说迷群体，与黑客文化不同，它早已明确承认"egoboo"（ego-boosting 的缩写，即提升自己在其他粉丝中声誉的行为）是志愿活动背后的基本驱动力。

Linus 成功地将自己定位为一个项目的守门人——在该项目中大部分开发工作由他人完成——并培育人们对该项目的兴趣直到它能够自我维持，这展现了对 Kropotkin 的"共同理解的原则"的敏锐把握。这种对 Linux 世界准经济学的视角使我们能够看到这种理解是如何被应用的。

我们可以将 Linus 的方法视为一种在"egoboo"中创造高效市场的方式——将个体黑客的自私性尽可能牢固地连接到只有通过持续合作才能实现的艰难目标上。通过 fetchmail 项目，我已经展示了（尽管规模较小）他的方法可以被复制并获得良好效果。也许我甚至比他更有意识、更系统化地做到了这一点。

许多人（尤其是那些在政治上不信任自由市场的人）会预期一个由自我驱动的 ego 主义者组成的文化是分裂的、领地意识强的、浪费的、保密的和充满敌意的。但这种预期显然被以下事实所证伪（仅举一例）：Linux 文档那令人叹为观止的多样性、质量和深度。程序员_讨厌_写文档，这是一个神圣的共识；那么，Linux 黑客们是如何产出如此之多文档的呢？显然，Linux 在 egoboo 方面的自由市场，比商业软件生产商那些耗资巨大的文档团队，更能产生有益的、利他的行为。

fetchmail 和 Linux 内核项目都表明，通过适当地奖励许多其他黑客的 ego，一个强大的开发者/协调者可以利用 Internet 来获取拥有大量共同开发者的好处，而又不会让项目陷入混乱的泥潭。因此，针对 Brooks 定律，我提出以下反命题：

> 19. 只要开发协调者拥有至少与 Internet 同样好的通信媒介，并且知道如何在不使用强制手段的情况下进行领导，那么众人的智慧必然胜过一人。

我认为开源软件的未来将越来越属于那些知道如何玩 Linus 这场游戏的人，那些抛弃大教堂、拥抱集市的人。这并不是说个人的远见和才华将不再重要；相反，我认为开源软件的前沿将属于那些从个人的远见和才华出发，然后通过有效地构建自愿的兴趣社区来放大其力量的人。

也许这不仅仅是开源软件的未来。没有任何闭源开发者能够匹敌 Linux 社区所能投入到一个问题上的才华储备。很少有谁能负担得起雇佣那超过 200（1999 年：600，2000 年：800）名为 fetchmail 做出贡献的人！

也许最终开源文化之所以会获胜，不是因为合作在道德上是正确的，也不是因为软件"囤积"在道德上是错误的（假设你相信后者的话——Linus 和我都不信），而仅仅是因为闭源世界无法在与开源社区的进化军备竞赛中取胜，后者能够在一个问题上投入数个数量级更多的熟练工时。

<h2 id="on-management-and-the-maginot-line">论管理与马奇诺防线</h2>

1997 年最初的《大教堂与集市》论文以上述愿景结尾——那是幸福的、网络化的程序员/无政府主义者大军，在竞争中胜出并碾压传统闭源软件的等级制度世界。

然而，许多怀疑论者并不信服；他们提出的问题值得认真对待。对集市论点的大多数反对意见归根结底是这样的主张：其支持者低估了传统管理的生产力倍增效应。

传统思维的软件开发管理者经常反对说，在开源世界中项目组如此随意地形成、变更和解散，这抵消了开源社区相对于任何单个闭源开发者在人数上的明显优势的很大一部分。他们会观察到，在软件开发中，真正重要的是随着时间推移的持续投入以及客户能够期望的对产品的持续投资，而不仅仅是有多少人在锅里扔了块骨头然后就任其炖着。

这个论点当然有几分道理；事实上，我在[《魔法大锅》](http://www.tuxedo.org/~esr/writings/magic-cauldron/)一文中已经阐述了预期未来服务价值是软件生产经济学关键的这一观点。

但这个论也有一个重大的隐含问题；它暗含着一个假设，即开源开发无法提供这样的持续投入。事实上，确实有一些开源项目在没有传统管理认为必不可少的激励结构或制度控制的情况下，在相当长的时期内保持了连贯的方向和有效的维护者社区。GNU Emacs 编辑器的开发就是一个极端而富有教益的例子；它吸收了数百名贡献者 15 年来的努力，形成了一个统一的架构愿景，尽管人员流动率很高，而且只有一个人（其作者）在整个期间始终活跃。没有任何闭源编辑器曾经匹配过这一长寿记录。

这提供了一个独立于大教堂与集市模式其他论点的理由来质疑传统管理的软件开发的优势。如果 GNU Emacs 能够在 15 年中表达一致的架构愿景，或者像 Linux 这样的操作系统能在硬件和平台技术快速变化的 8 年中做到同样的事情；并且如果（事实上确实如此）已经有许多架构良好的、持续时间超过 5 年的开源项目——那么我们完全有理由质问，传统管理的巨大开销实际上到底给我们带来了什么。

无论它带来了什么，肯定都不包括按时、按预算或按照规格说明书的所有功能可靠地执行；一个"被管理"的项目能同时满足这三个目标中的一个都很少见，更不用说全部三个了。它似乎也不包括在项目生命周期内适应技术和经济环境变化的能力；在这方面开源社区已被证明远为有效（例如，任何人都可以轻松验证这一点：将 Internet 30 年的历史与专有网络技术的短暂半衰期相比较，或者将 Microsoft Windows 从 16 位到 32 位转换的成本与同一时期 Linux 几乎毫不费力地向上迁移相比较——后者不仅沿着 Intel 的开发路线，还迁移到了十几个其他硬件平台上，包括 64 位的 Alpha）。

许多人认为传统模式能买到的一件事是：当项目出了问题时，有人可以在法律上被追究责任并可能从中获得赔偿。但这是一种错觉；大多数软件许可证都明确声明不承担任何担保责任，更不保证性能——而成功追索软
不履约的情况极其罕见。即便这种情况很常见，因为有人可以起诉而感到安慰，也未免偏离了要点。你不想陷入诉讼；你想要的是能正常运行的软件。

那么，所有这些管理开销到底换来了什么？

为了理解这一点，我们需要了解软件开发管理者认为自己做了什么。我认识一位似乎非常擅长这项工作的女性，她说软件项目管理有五项功能：

- _定义目标_，让所有人朝着同一个方向努力
- _监督_，确保关键细节不被遗漏
- _激励_ 人们去做枯燥但必要的苦差事
- _组织_ 人员部署以实现最佳生产力
- _调配_ 维持项目所需的资源

这些都是看似值得追求的目标；但在开源模式及其周边的社会环境中，它们却开始显得莫名其妙地无关紧要。我们倒序来逐一讨论。

我的朋友说，大量的_资源调配_工作本质上是防御性的；一旦你拥有了人员、设备和办公空间，你就得保护它们，防止同级管理者争夺同样的资源，也要防止高层试图对有限的资源池进行最高效的分配。

但开源开发者是志愿者，他们凭借对所参与项目的兴趣和贡献能力而自主选择加入（即使他们拿薪水上班写开源代码，这一点也大体成立）。志愿精神往往会自动解决资源调配中"进攻"的一面；人们自带资源参与其中。而管理者几乎不需要在传统意义上"打防守"。

无论如何，在一个个人电脑廉价、互联网连接快速的世界里，我们始终发现，唯一真正稀缺的资源是 skilled attention（技术人才的注意力）。开源项目即使陷入困境，也几乎从来不是因为缺少设备、网络或办公空间；它们只在开发者自身丧失兴趣时才会消亡。

既然如此，开源黑客通过自我选择来实现最高生产力的_自主组织_就显得加倍重要——而社交环境对能力的选择是无情的。我的朋友同时熟悉开源世界和大型闭源项目，她认为开源之所以成功，部分原因在于其文化只接纳编程人群中大约最顶尖的5%的人才。她大部分时间都在组织另外95%的人员部署，因此亲眼观察到了一个众所周知的现象：最有能力的程序员与仅仅称职的程序员之间，生产力差距高达一百倍。

如此巨大的差距一直引出一个尴尬的问题：如果不是那些能力最弱的50%以上的人参与其中，个别项目乃至整个行业是否会更好？有思想的管理者早就明白，如果传统软件管理的唯一功能就是把能力最弱者从净损失转变为微利，那这笔买卖可能并不划算。

开源社区的成功大大加剧了这一质疑，因为它提供了确凿的证据：从互联网上招募自主选择的志愿者，往往比管理一整栋宁愿去做别的事情的人更便宜、更有效。

这就自然地引出了_激励_的问题。我朋友的观点有一个等价的、常被提及的说法：传统开发管理是对缺乏激励的程序员的必要补偿——如果没有管理，他们不会做出好的工作成果。

这种说法通常还伴随着一种论调，即开源社区只能被指望去做那些"性感"的或技术上精妙的工作；其他任何事情都会被搁置（或做得很差），除非由金钱驱动的格子间打工人在管理者挥舞鞭子下完成。我在_[Homesteading the Noosphere](http://www.catb.org/esr/writings/homesteading/homesteading/)_一书中探讨了对这一说法持怀疑态度的心理和社会原因。但就目前而言，我认为指出接受这一说法为真所带来的启示更为有趣。

如果传统的、闭源的、高度管理的软件开发风格真的只是靠一道类似马奇诺防线的无聊问题来防御，那么在每个具体应用领域中，它只能维持到没有人觉得这些问题真正有趣、也没有人找到绕过它们的方法之前。因为一旦某个"无聊"的软件有了开源竞争，客户就会知道，终于有人因为对问题本身的痴迷而选择去解决它——在软件开发以及其他创造性工作中，这种内在驱动力远比金钱更有效。

因此，仅仅为了激励而设立传统管理结构，也许是好战术但却是坏战略；短期或许能赢，但长期注定会输。

到目前为止，传统开发管理在两个方面（资源调配、组织）看起来都已经输给了开源，在第三个方面（激励）上也只是在苟延残喘。而备受困扰的传统管理者在监督问题上也得不到任何安慰；开源社区最强的论据恰恰在于，去中心化的同行评审胜过了所有确保细节不被遗漏的传统方法。

我们能否把_定义目标_保留为传统软件项目管理开销的正当理由？也许可以；但要做到这一点，我们需要有充分的理由相信，管理委员会和企业路线图在定义值得追求且被广泛认同的目标方面，比开源世界中扮演类似角色的项目领导者和"部落长老"更成功。

这乍一看是一个非常难以论证的命题。让这个命题难以成立的，与其说是天平上开源那一边的筹码（Emacs的长久生命力，或 Linus Torvalds 用"统治世界"的口号动员大批开发者的能力），不如说是传统机制在定义软件项目目标方面所展现出的糟糕表现。

软件工程领域最著名的民间定理之一是：60%到75%的传统软件项目要么从未完成，要么被目标用户拒绝。如果这个区间大致正确（而我从未见过任何有经验的管理者对此提出异议），那么超过一半的项目所瞄准的目标要么（a）不切实际地无法达成，要么（b）完全错误。

这个问题，比其他任何问题都更严重地说明了为什么在当今的软件工程世界中，"管理委员会"这个说法很可能会让听者脊背发凉——即使（或者尤其是因为）听者本身是一位管理者。只有程序员才抱怨这种现象的日子早已过去了；如今 Dilbert 漫画也挂在了_高管_的办公桌上方。

因此，我们对传统软件开发管理者的回答很简单——如果开源社区真的低估了传统管理的价值，_那为什么你们当中那么多人对自己的流程嗤之以鼻？_

开源社区的例子再次大大加剧了这一质疑——因为我们在做自己做的事情时感到_快乐_。我们的创造性游戏一直在以惊人的速度取得技术、市场份额和心智占有率上的成功。我们不仅在证明自己能做出更好的软件，而且在证明_快乐本身就是一种资产_。

在本文第一版发表两年半之后，我能提出的最激进的想法已经不再是开源主导软件世界的愿景；毕竟，如今许多西装革履的严肃人士也觉得这是说得通的。

相反，我想提出一个可能更广泛的启示，它不仅适用于软件，（而且可能适用于每一种创造性或专业工作）。人类通常会在任务处于某种最佳挑战区间时感到愉悦；不太简单以至于无聊，也不太难以至于无法实现。一个快乐的程序员既不会被闲置，也不会被糟糕的目标设定和充满压力的流程摩擦所压垮。_享受感预示着效率。_

因此，对自己的工作流程怀有恐惧和厌恶（即使是以挂 Dilbert 漫画这种含蓄而反讽的方式表达），本身就应被视为流程失败的一种信号。快乐、幽默和好玩确实是资产；我上文写到"快乐的黑客大军"并非仅仅是为了押头韵，Linux 的吉祥物是一只可爱的、幼态延续的企鹅，这也绝非仅仅是个玩笑。

很可能，开源成功最重要的效果之一，将是教会我们：_玩耍是创造性工作中最具经济效益的模式_。

<h2 id="epilog">尾声：Netscape 拥抱集市</h2>

意识到自己正在参与创造历史，是一种奇妙的感觉……

1998年1月22日，在我首次发表_《大教堂与集市》_大约七个月之后，Netscape Communications, Inc. 宣布计划[开源 Netscape Communicator](http://www.netscape.com/newsref/pr/newsrelease558.html)。在公告发布当天之前，我对这件事即将发生一无所知。

Netscape 的执行副总裁兼首席技术官 Eric Hahn 在公告发布后不久给我发了封电子邮件："代表 Netscape 的所有人，我想感谢你在第一时间帮助我们走到了这一步。你的思想和著作是我们做出这一决定的基础性灵感。"

接下来的一周，我应 Netscape 之邀飞往硅谷，与他们的高层管理者和技术人员参加了一整天的战略会议（1998年2月4日）。我们共同设计了 Netscape 的源代码发布策略和许可证。

几天后我写道：

> Netscape 即将为我们提供一个大规模的、在商业世界中验证集市模式的真实试验。开源文化现在面临着一个危险：如果 Netscape 的执行不成功，开源概念可能会被严重质疑，以至于商业世界在接下来的十年里都不会再碰它。
>
> 另一方面，这也是一个绝佳的机会。华尔街和其他地方对这一举措的初步反应是谨慎积极的。我们也得到了证明自己的机会。如果 Netscape 通过这一举措重新获得可观的市场份额，它很可能将在软件行业引发一场早已 overdue 的革命。
>
> 未来一年应该是非常有教益和有趣的。

确实如此。在我执笔的2000年年中，后来被命名为 Mozilla 的项目的开发只是取得了有保留的成功。它实现了 Netscape 最初的目标，即阻止 Microsoft 在浏览器市场上获得垄断地位。它也取得了一些引人注目的成就（尤其是下一代 Gecko 渲染引擎的发布）。

然而，它还没有从 Netscape 外部获得 Mozilla 创始人最初期望的大规模开发力量。这里的问题似乎在于，很长一段时间里，Mozilla 的发行实际上违反了集市模式的一条基本规则：它没有提供潜在贡献者可以轻松运行和看到效果的东西。（在发布后超过一年的时间里，从源代码构建 Mozilla 需要专有 Motif 库的许可证。）

最令人沮丧的是（从外部世界的角度来看），Mozilla 团队在项目启动两年半之后仍未发布一个生产级浏览器——而且在1999年，该项目的一位核心成员因抱怨管理不善和错失良机而辞职，引起了不小的轰动。"开源，"他准确地指出，"不是魔法 pixie dust。"

它确实不是。Mozilla 的长期前景现在（2000年11月）看起来比 Jamie Zawinski 辞职信发布时好得多——在过去几周里，每夜构建版本终于跨过了生产可用性的关键门槛。但 Jamie 正确地指出，仅仅开放源代码并不一定能拯救一个已经饱受目标不清、代码混乱或其他软件工程慢性疾病困扰的项目。Mozilla 同时为我们提供了一个开源如何成功以及如何失败的例子。

然而与此同时，开源理念在其他地方也取得了成功并找到了支持者。自 Netscape 开源以来，我们看到了对开源开发模式的兴趣的巨大爆发，这一趋势既受到 Linux 操作系统持续成功的推动，也在反过来推动着 Linux 的成功。Mozilla 所引发的趋势正在以加速的态势延续。

  <li id="fnIN">
    <p><em>[IN]</em> 一个与能否从零开始以集市模式启动项目相关的问题是：集市模式是否能够支持真正的创新性工作。有人声称，由于缺乏强有力的领导，集市只能处理对现有工程最前沿理念的克隆和改进，而无法推动最前沿的发展。这种论点最臭名昭著的表达也许是<a href="http://www.opensource.org/halloween/">万圣节文档</a>——两份关于开源现象的令人尴尬的 Microsoft 内部备忘录。作者们将 Linux 开发类 Unix 操作系统比作"追着尾灯跑"，并断言"（一旦项目与最前沿实现了'平齐'），推进到新前沿所需的管理力度就会变得巨大。"</p>
    <p>这种论点暗示了严重的事实性错误。万圣节文档的作者们自己后来观察到的一个事实就揭示了这一点："通常[……]新的研究理念首先在 Linux 上被实现和提供，然后才在其他平台上出现或被纳入。"</p>
    <p>如果我们把"Linux"读作"开源"，就会发现这远非新现象。从历史上看，开源社区并不是靠追着尾灯跑或被大规模管理才发明了 Emacs、万维网或者互联网本身——而在当下，开源领域有如此多的创新工作正在进行，以至于让人目不暇接。仅举众多例子中的一个，GNOME 项目就在 GUI 和对象技术方面大力推动了最前沿的发展，以至于在 Linux 社区之外的计算机行业媒体上也引起了广泛关注。其他例子不胜枚举，任何一天去看看 <a href="http://freshmeat.net/">Freshmeat</a> 就能迅速证实这一点。</p>
    <p>但在隐含假设中存在一个更根本性的错误，即认为_大教堂模式_（或集市模式，或任何其他管理结构）能够以某种方式可靠地推动创新。这是无稽之谈。群体不会有突破性的洞见——即使是集市无政府主义者的志愿群体也通常缺乏真正的原创性，更不用说那些在现状中存在生存利益的 corporate committee 了。_洞见来自个人。_ 他们周围的社交机制所能期望做到的，最多不过是_回应_突破性的洞见——去滋养它们、奖励它们、严格地检验它们，而不是压制它们。</p>
    <p>有些人会将此定性为一种浪漫主义的看法，是对过时的独行侠发明家形象的回归。并非如此；我并不是说群体在某人_已经_有
经被酝酿出来；事实上，我们从同行评审过程中了解到，这样的开发小组对于产出高质量成果是至关重要的。我倒是想指出，每一个这样的小组开发都始于——必然由——某个人头脑中的一个好点子所激发。大教堂和集市以及其他社会结构可以捕获那道闪电并加以提炼，但它们无法按需制造它。</p>
    <p>因此，创新（无论在软件还是其他领域）的根本问题确实是如何不被扼杀——但更根本地，它是<em>如何培养出大量能够最初产生洞见的人。</em></p>
    <p>假设大教堂式的开发能够做到这一点，而集市的低准入门槛和流程流动性却不能，那是荒谬的。如果所需要的是一个人带着一个好点子，那么在一种社会环境中，这个人能够迅速吸引成百上千人围绕这个好点子合作，这种环境必然会在创新方面超越另一种环境——在后一种环境中，这个人必须先向层级体系做政治推销，才能在没有被解雇风险的情况下着手实现自己的想法。</p>
    <p>而且，确实如此，如果我们回顾采用大教堂模式的组织的软件创新历史，很快就会发现这相当罕见。大公司依赖大学研究来获取新想法（因此《万圣节文档》的作者们对 Linux 快速吸收研究成果的能力感到不安）。或者他们收购围绕某个创新者的大脑建立的小公司。无论哪种情况，创新都不是大教堂文化所固有的；事实上，许多这样引入的创新最终都在《万圣节文档》作者们如此推崇的"大规模管理层"下被悄悄扼杀了。</p>
    <p>不过，这是一个消极的论点。读者最好由一个积极的论点来服务。我建议做以下实验：</p>
    <ul>
      <li>
        <p>选择一个你认为可以一致应用的原创性标准。如果你的定义是"我看到就知道"，那对这个测试来说也不是问题。</p>
      </li>
      <li>
        <p>选择任何一个与 Linux 竞争的闭源操作系统，以及一个获取其当前开发工作最佳信息的来源。</p>
      </li>
      <li>
        <p>观察那个来源和 Freshmeat 一个月。每天计算你在 Freshmeat 上认为属于"原创"工作的发布公告数量。将同样的"原创"定义应用于那个其他操作系统的公告，并计算数量。</p>
      </li>
      <li>
        <p>三十天后，合计两个数字。</p>
      </li>
    </ul>
    <p>我写这篇文章的那天，Freshmeat 上有二十二条发布公告，其中三条似乎在某些方面可能推动了现有技术水平的发展。这对 Freshmeat 来说还是个慢日子，但如果有读者报告在任何闭源渠道中<em>一个月</em>内能看到多达三项可能的创新，我会感到非常惊讶。&nbsp;<a href="#refIN">↩</a></p>
  </li>

  <li id="fnEGCS">
    <p><em>[EGCS]</em> 我们现在有了一个项目的历史，它在若干方面可能提供了比 fetchmail 更具指示性的集市前提测试：<a href="http://egcs.cygnus.com/">EGCS</a>，即实验性 GNU 编译器系统（Experimental GNU Compiler System）。</p>
    <p>这个项目于1997年8月中旬宣布，是有意识地尝试将《大教堂与集市》早期公开版本中的理念付诸实践。项目创始人认为 GCC（GNU C 编译器）的开发已经停滞不前。在随后的约二十个月中，GCC 和 EGCS 作为并行产品继续发展——两者都从同一个互联网开发者群体中汲取力量，都从同一个 GCC 源代码库起步，都使用基本相同的 Unix 工具集和开发环境。两个项目的区别仅在于：EGCS 有意识地应用了我之前描述的集市策略，而 GCC 则保留了更像大教堂的组织方式，包括封闭的开发者群体和不频繁的发布。</p>
    <p>这几乎是我们所能期望的最接近对照实验了，结果令人震惊。几个月内，EGCS 版本在功能上已经大幅领先：更好的优化、对 FORTRAN 和 C++ 更好的支持。许多人发现 EGCS 的开发快照比 GCC 最新稳定版本更可靠，主要的 Linux 发行版开始转向 EGCS。</p>
    <p>1999年4月，自由软件基金会（GCC 的官方赞助者）解散了原来的 GCC 开发小组，并正式将项目控制权移交给 EGCS 指导团队。&nbsp;<a href="#refEGCS">↩</a></p>

  <li id="fnSP">
    <p><em>[SP]</em> 当然，Kropotkin 的批评和 Linus 定律引发了一些关于社会组织控制论的更广泛问题。软件工程的另一个民间定理提出了其中之一：Conway 定律——通常表述为"如果你有四个小组在开发一个编译器，你就会得到一个四遍编译器"。最初的陈述更为一般化："设计系统的组织受到约束，只能产出这些组织沟通结构的副本。"我们可以更简洁地表述为"手段决定结果"，甚至"过程即产品"。</p>
    <p>因此值得注意，在开源社区中，组织形式和功能在多个层面上是匹配的。网络无处不在：不仅是互联网，做工作的人也形成了一个分布式、松耦合、点对点的网络，提供多重冗余并能非常优雅地降级。在两种网络中，每个节点的重要性仅取决于其他节点是否愿意与之合作。</p>
    <p>点对点这一特性对社区惊人的生产力至关重要。Kropotkin 试图阐述的关于权力关系的观点被"SNAFU 原则"进一步发展："真正的沟通只能在平等者之间进行，因为下属因告诉上级悦耳的谎言而获得的回报，比告诉真相更稳定。"创造性的团队协作完全依赖于真正的沟通，因此严重受到权力关系存在的阻碍。开源社区实际上没有这种权力关系，通过对比向我们展示了这些关系在 bug、降低生产力和错失机会方面代价有多么惨重。</p>
    <p>此外，SNAFU 原则预言，在威权组织中，决策者与现实之间会出现渐进式的脱节，因为输入给决策者的信息越来越多地变成悦耳的谎言。这在传统软件开发中的表现显而易见；下属有强烈的动机去隐藏、忽视和最小化问题。当这个过程变成产品时，软件就成了灾难。&nbsp;<a href="#refSP">↩</a></p>
  </li>
</ul>

<h2 id="bibliography">参考文献</h2>

我引用了 Frederick P. Brooks 的经典著作《人月神话》（_The Mythical Man-Month_）中的若干片段，因为在许多方面，他的见解至今无人能超越。我衷心推荐 Addison-Wesley 出版的25周年纪念版（ISBN 0-201-83595-9），该版增加了他1986年的论文《没有银弹》（"No Silver Bullet"）。

新版以一篇极具价值的二十年后回顾作结，在其中 Brooks 坦率地承认了原文中少数经不起时间考验的判断。我在本文第一个公开版本基本完成后才读到这篇回顾，惊讶地发现 Brooks 将类似集市的做法归因于 Microsoft！（然而，事实上这个归属后来被证明是错误的。1998年我们从[万圣节文档](http://www.opensource.org/halloween/)中了解到，Microsoft 的内部开发者社区严重割裂，支持集市所需的那种普遍的源代码访问实际上根本不可能实现。）

Gerald M. Weinberg 的《计算机编程心理学》（_The Psychology Of Computer Programming_，纽约，Van Nostrand Reinhold 1971年出版）引入了一个标签不太恰当的概念——"无自我编程"（egoless programming）。虽然他远非第一个认识到"命令原则"之徒劳的人，但他可能是第一个在软件开发这一特定背景下认识并论证这一观点的人。

Richard P. Gabriel 在审视 Linux 之前的 Unix 文化时，在他1989年的论文"LISP: Good News, Bad News, and How To Win Big"中不情愿地为一种原始的类似集市模式的优越性进行了论证。尽管在某些方面已经过时，这篇文章仍然受到 LISP 爱好者（包括我）的推崇。一位通信者提醒我，其中标题为"Worse Is Better"的一节读起来几乎像是对 Linux 的预言。该论文可在万维网上获取：[http://www.naggum.no/worse-is-better.html](http://www.naggum.no/worse-is-better.html)。

De Marco 和 Lister 的《人件：高效的项目与团队》（_Peopleware: Productive Projects and Teams_，纽约；Dorset House，1987年；ISBN 0-932633-05-6）是一颗被低估的宝石，我很高兴看到 Fred Brooks 在他的回顾中引用了它。虽然作者所说的大部分内容并不能直接适用于 Linux 或开源社区，但作者对创造性工作所需条件的洞察非常敏锐，对于任何试图将集市模式的一些优点引入商业环境的人来说都很有价值。

最后，我必须承认，我几乎把这篇文章命名为"The Cathedral and the Agora"——后者是希腊语，意为开放的集市或公共集会场所。Mark Miller 和 Eric Drexler 撰写的开创性"agoric systems"系列论文，通过描述类市场计算生态系统的涌现特性，帮助我清晰地思考了五年后 Linux 让我面对的开源文化中的类似现象。这些论文可在以下网址获取：[http://www.agorics.com/agorpapers.html](http://www.agorics.com/agorpapers.html)。
